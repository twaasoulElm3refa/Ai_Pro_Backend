Date: 2026-07-19
Branch: codex/wallet-deposit-hardening

1) Executive summary
====================
The PayPal wallet-deposit flow was rebuilt around one authoritative completion path:
PayPal verified capture COMPLETED -> validate all payment identity fields -> one locked DB transaction -> credit wallet once -> create one ledger row -> mark payment completed -> queue email after commit.

The browser return URL is no longer a source of truth. It only moves a pending payment to approved and redirects to the waiting page. Completion can occur through a verified webhook, the capture response for CHECKOUT.ORDER.APPROVED, or the reconciliation command; all three call finalizeCompletedWalletCapture().

No .env secret was displayed, changed, or committed. Hard-coded frontend API URL/key values were removed. The pre-existing untracked AI_PRO_WALLET_DEPOSIT_FULL_AUDIT.txt was preserved unchanged.

2) Problems fixed and why
=========================
- Webhook authenticity: PayPal signature verification is enabled by default, requires all five PayPal signature headers plus PAYPAL_WEBHOOK_ID, and accepts only SUCCESS. Disabling verification is allowed only in local/testing; production fails closed.
- Webhook idempotency: paypal_webhook_events records event_id (unique), type, order/capture IDs, payload, processing state, errors, and processed_at. Repeated processed events return HTTP 200 without repeating financial work.
- Financial validation: status, event path, PayPal order ID, real capture ID, custom_id, optional reference_id, exact integer-minor-unit amount, currency, configured merchant ID, wallet_deposit type, and an existing owner are validated before credit.
- Capture identity: Order Capture and Capture Webhook response shapes are both supported; transaction_id stores the PayPal Capture ID, never the Order ID.
- Atomicity/concurrency: Payment and Wallet use lockForUpdate inside a retrying DB transaction. Wallet credit, WalletTransaction creation, and Payment completion commit or roll back together.
- Database guarantees: unique capture ID, payment ledger row, ledger slug, and webhook event ID prevent duplicate credit even under retries/concurrency. Wallet/ledger numeric columns were widened to unsigned BIGINT.
- Existing data safety: completed wallet payments are backfilled to wallet_credited=true only when a matching ledger row already exists.
- Email safety: success/failure mail is handled by unique queue jobs after commit. mail_sent changes only after the mailer succeeds. Mail failure is logged/retried and never reverts a completed payment.
- Idempotent creation/capture: client UUIDs are scoped to the user and persisted in sessionStorage across a lost response. Deterministic PayPal-Request-Id values are used for create and capture calls. A semantic duplicate APPROVED event cannot capture a completed payment again.
- Wallet arithmetic: no float is used. USD is converted to integer cents, then points using WALLET_POINTS_PER_USD (currently intended scale: 1 USD = 1,000,000 points), with configuration and overflow checks. balance_after is taken after refresh().
- Status privacy: orderStatus is authenticated, owner-scoped, wallet-deposit scoped, and returns only order_id/status/amount/currency/paid_at.
- Frontend lifecycle: approved is transient, only completed is success, polling is sequential setTimeout-based, overlapping requests are blocked, AbortController handles unmount, and polling stops on completed/failed/timeout/error. 401/403/404/429/5xx have explicit behavior and navigation uses router.replace(). Timeout is not presented as a final payment failure.
- Reconciliation: payments:reconcile-paypal-wallet checks old pending/approved deposits against PayPal and reuses the same finalizer. It is scheduled every five minutes without overlap.
- Observability: webhook_received, webhook_verified, webhook_duplicate, payment_validation_failed, wallet_credit_started, wallet_credit_committed, email_queued, email_failed, reconciliation_started, and reconciliation_completed are emitted without credentials/tokens/card data.

8) Manual Sandbox verification
==============================
1. Configure Sandbox client credentials, the Sandbox webhook ID, the exact receiving Sandbox merchant ID, PAYPAL_VERIFY_WEBHOOK=true, an HTTPS APP_URL reachable by PayPal, and the required public VITE build values. Do not commit them.
2. In the PayPal Sandbox app, set the webhook URL to:
   https://<host>/api/v1/paypal/webhook
   Subscribe to CHECKOUT.ORDER.APPROVED, PAYMENT.CAPTURE.COMPLETED, and PAYMENT.CAPTURE.DECLINED.
3. Run php artisan optimize:clear, php artisan migrate --force, npm run build.
4. Ensure the scheduler and Redis queue worker are running. The current scheduler starts a stop-when-empty worker every minute and reconciliation every five minutes.
5. Sign in as a normal user, create a small deposit, approve with a Sandbox buyer, and verify the waiting page does not treat approved as completed.
6. Verify exactly one Payment becomes completed with wallet_credited=true, a real Capture ID in transaction_id, paid_at set, one WalletTransaction, and one wallet increment.
7. Resend the same webhook from PayPal and confirm HTTP 200 plus no second ledger row/increment.
8. Test cancel, browser close/no return, delayed webhook, and temporary queue/mail outage. Browser close must still complete via webhook/reconciliation; mail failure must leave payment completed.
9. Inspect only sanitized log context for the event names listed above. Never log credentials, access tokens, raw authorization headers, or card data.

Automated tests use PayPal/Mail/Queue mocks and intentionally make no real PayPal call.

10) Rollback plan
=================
1. Stop new wallet deposits and pause the reconciliation schedule/queue consumers for this feature.
2. Preserve a DB backup and export paypal_webhook_events plus affected payments/wallet_transactions before any schema rollback; do not delete financial audit data casually.
3. Roll back application/frontend code to the previous release and rebuild assets.
4. If schema rollback is truly required and no new release depends on it, run:
   php artisan migrate:rollback --step=1
   This drops paypal_webhook_events, wallet_credited, and the two new wallet transaction unique indexes. It intentionally does not shrink BIGINT columns because narrowing balances can overflow or lose data.
5. Re-enable traffic only after reconciling all PayPal captures created during the rollout window. Never manually decrement credited wallets without an audited compensating transaction.
6. Keep webhook verification enabled during rollback. If the old application cannot safely process events, temporarily pause the PayPal webhook/feature and reconcile before resuming.
